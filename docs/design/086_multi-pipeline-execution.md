## 1. 一句话结论

现在的「多节点运行」不是慢在算力，而是**执行单元选错了**：它把图拆成一条条完整路径，路径之间重复跑公共前缀，进度只有一个「第几条路径」，结果只能在底栏堆页签。

建议分两步走：

1. **先做方案 A（运行清单）**：不改执行语义，只把「跑哪几条、跑到哪、结果属于谁」变成看得见、点得动；执行前的分支选择挂进菜单栏的「执行」（全部 / 部分 / 只跑一条），底栏「运行」只做进度与结果。风险低，能立刻消除大部分困惑。
2. **再做方案 B 的最小版（共享段只跑一次 + 段级并发）**：只解决重复计算与串行，不在这一步改多入边语义。多入边单独评审。

方案 C（管道作业台）**不单独做**，只吸收它「跨标签页运行清单」的部分，并入 A/B 的面板。

## 2. 现状：一次「执行」到底发生了什么

```
handleExecute
  └─ executeForTab(tab)                 校验必填参数、收集 {{变量}}
       └─ runPipeline(pending, ctx)
            ├─ buildExecutionBranches(steps, edges)   → PipelineStep[][]（路径列表）
            ├─ branches>1 且 outputPath 非空           → 阻塞式覆盖确认
            └─ for (i = 0..branches.length) await executeSingleBranch(...)
                 ├─ batch 分支 → 前端批量钩子
                 ├─ chart 分支 → 前端 recharts 渲染
                 └─ 普通分支   → 一次 invoke，后端拼线性子进程链
            └─ finally：结果预览、节点错误、执行历史、完成 toast
```

### 2.1 五个结构事实

| # | 事实 | 代码 |
|---|------|------|
| 1 | **分支 = 路径，不是节点集**。菱形 `A→(B,C)→D` 产出 `[A,B,D]`、`[A,C,D]` 两条，A 与 D 各跑两次 | `buildBranches.ts:61-68` |
| 2 | 一条分支 = 一次 `execute_xan_pipeline`，只接受一条线性链 | `executeBranch.ts:175-213` |
| 3 | 进度是单值 `{current,total,name,status}`，同一时刻只描述「当前分支」 | `types/execution.ts:13-18`、`HomeView.tsx:539-614` |
| 4 | 结果 = 每个成功分支一个 `ResultPreview`，底栏一个页签；失败分支不产页签 | `runPipeline.ts:172-198`、`App.tsx:876-893` |
| 5 | 节点没有运行态，只有 `step.error`；运行中画布是静止的 | `PipelineStepNode.tsx:340-347` |

### 2.2 一次运行的时序（菱形图）

```
分支 1/2   A → B → D      A 重跑      D 重跑
分支 2/2   A → C → D
```

`A` 与 `D` 被计算两次，`outputPath` 被注入两次（每个分支的最后一步），后写覆盖先写。

## 3. 诊断

按「正确性 → 可见性 → 性能」排序。

### P0 正确性与语义

| # | 问题 | 证据 / 影响 |
|---|------|-------------|
| P0-1 | **共享前缀重复执行**。分支数随分叉层数指数增长，公共前缀重复次数同步增长 | `buildBranches.ts:66-68`；大文件下是成倍 IO 与 CPU |
| P0-2 | **多入边没有汇聚语义**。D 有两条入边时被当成两条路径的成员，每次只吃到一条前驱的数据；用户无法在画布上表达「合并 B、C 再处理」，只能用 join/cat 命令，且 UI 没有任何提示 | `buildBranches.ts:31-35` |
| P0-3 | **多分支写同一个输出**。`outputPath` 注入每条分支最后一步，串行写同一文件；执行前只有一次阻塞确认，执行中无提示。取消或中途失败还可能留下半截文件 | `executeBranch.ts:189-195`、`runPipeline.ts:75-85` |
| P0-4 | **部分失败被折叠成一个状态**。一条分支失败后其余继续跑，最终 toast 报「执行失败」，成功分支的结果仍在；用户不知道哪几条跑了、哪几条没跑 | `runPipeline.ts:218-234`、`:238-245` |

### P1 可见性与交互

| # | 问题 | 影响 |
|---|------|------|
| P1-5 | 看不到「当前执行到哪个节点」，也看不到已成功节点；节点只在失败时变红 | 长链路等待时没有任何位置感 |
| P1-6 | 结果页签叫「结果 1 / 2 / 3」，meta 是步骤链；相同前缀的分支几乎无法区分 | 多分支时页签爆满，无法回答「这份结果来自哪条分支」 |
| P1-7 | 执行前没有计划预览。点下「执行」才知道有 N 条分支、要写同一个文件、要跑 30 次步骤 | 覆盖确认来得太晚 |
| P1-8 | 分支不可单独运行 / 重跑 / 取消。取消只能取消整个 run，剩余分支直接不再执行，且 UI 没有「未执行」标记 | 一条坏分支拖垮整轮 |
| P1-9 | 「从该步运行」是旁路：要求用户先手动导出上一步的中间 CSV，再选文件；不能复用本次运行结果 | `useRunFromStep.ts:63-82`、`useSaveIntermediate.ts` |

### P2 性能与工程化

| # | 问题 | 影响 |
|---|------|------|
| P2-10 | **分支串行**：互不依赖的分支逐个 await，总耗时 = 各分支之和；后端 `spawn_blocking` 与多标签并发早已支持并行 | 三路分支就是三倍等待 |
| P2-11 | 没有中间结果复用：同一次运行内重复前缀、跨运行同一前缀都要重算 | 反复调下游时成本最高 |

## 4. 三个方案

### 方案 A：运行清单（Branch Run List）

**一句话**：执行模型不动，补上「选择、计划、状态、归属」四件事。

#### A1 执行前：选择要运行的分支

`branches.length > 1` 时不再直接弹覆盖确认，而是展开**分支选择**：默认全选，用户可以取消任意行，也可以只运行其中一条。

> P0 的入口在菜单栏「执行」里（见 A6）；本节先定义内容与状态，原型 02 展示完整尺寸，原型 05 展示菜单内的紧凑版。

```
‹ 返回  销售清洗
[✓] 全选                              已选 2 / 3
──────────────────────────────────────────────
[✓] 01  filter › groupby      2 步         只运行
[✓] 02  filter › sort         2 步         只运行
[ ] 03  filter › dedup        2 步         只运行
──────────────────────────────────────────────
输出 out.csv 将被覆盖 2 次
选择要运行的分支             [取消]  [运行所选 2 条]
```

- 默认全选；表头复选框在部分选中时显示半选，点击一次全选、再点一次全不选。
- 主按钮文案随选择变化：`运行全部 3 条` / `运行所选 2 条` / `选择分支`（0 条时禁用）。
- 行尾「只运行」立即以该分支单独开始，等价于「只勾这一条再确认」，不再弹第二次确认。
- 全选行右侧只显示已选计数（`已选 2 / 3`），不再单列步数 / 去重步数；输出覆盖次数按已选分支实时计算，只选 1 条时覆盖提示改为「将写入 1 次」。
- 选择级不设单独标题行；底栏左侧常驻「选择要运行的分支」，不再显示「未选分支不执行」之类的补充提示。
- **未选中的分支不进入本次 run**：不执行、不生成结果、不占并发槽，也不在画布上标 `skipped`（它从未开始）。
- 单分支 / 单链管道不出现选择级，点执行直接跑（保持现状，零回归）。
- 选择不持久化；下一次执行默认回到全选，避免「上次漏跑」被静默延续。

#### A1.1 三条路径

| 用户意图 | 操作 | 结果 |
|----------|------|------|
| 全部运行 | 保持默认全选，点「运行全部 3 条」 | 与今天一致，逐条串行 |
| 运行其中几条 | 取消不需要的行，点「运行所选 2 条」 | 只跑选中的分支，结果页签也只有这些 |
| 只运行某一条 | 点该行「只运行」 | 立刻只跑这一条，其余留在「未运行」 |
| 暂不运行 | Esc / 取消 | 不产生 run session，不占槽位 |

#### A1.2 运行后再跑剩余

一次只选部分分支时，运行面板底部保留一行弱提示：

```
3 条分支中有 1 条未运行                          [运行剩余]
```

点击「运行剩余」重新打开执行菜单的选择级，并把上次未选中的分支预勾选；已跑过的分支不自动重跑。

#### A2 运行中：一行一分支

底栏新增固定页签「运行」，位置在「日志」之后、「结果」之前。清单**只列本次选中的分支**：

| 序号 | 分支链 | 状态 | 当前步骤 | 耗时 | 操作 |
|------|--------|------|----------|------|------|
| 01 | filter › groupby | 运行中 | groupby | 0:12 | 取消 |
| 02 | filter › sort | 完成 | — | 0:08 | 结果 · 重跑 |

- 顶部汇总只统计选中分支：`1 运行中 · 1 完成` + 总进度条（按选中分支数）。
- 如果有未选中的分支，清单底部追加一行弱提示 `3 条分支中有 1 条未运行 · 运行剩余`，不占分支行。
- 每行可单独取消是 P1：P0 只有整轮取消（沿用画布 pill 的按钮），运行面板不提供行内取消，避免「取消整轮」被误读成「只停这一条」。
- 行高 34px，序号与耗时走等宽 `tabular-nums`，状态用 6px 灯 + 文字，不用彩色胶囊。

#### A3 画布：节点状态

新增**不持久化**的 `executionStates: Record<stepId, "pending" | "running" | "done" | "error" | "skipped">`（不写进 `step`，避免高频 `setTabs` 抖动）：

- `running`：卡片左缘 2px 墨蓝竖条 + 序号处一个小实心点（静态，不做呼吸动画）。
- `done`：序号芯片填实，颜色退成次要文字。
- `error`：沿用现有红框 + 错误块。
- `skipped`：整卡 60% 不透明度，不置灰文字。只用于「本次选中、但被失败策略跳过」的节点。
- **未选中分支上的节点保持常态**，不进入 `executionStates`：它们没有开始过，不应该看起来像失败或被跳过。
- 同一节点在第二条分支再次执行时，显示 `已跑 2 次` 角标 —— 把 P0-1 暴露出来，而不是继续藏着。

#### A4 结果归属

- 页签文案从「结果 1」改为「分支 01」，`title` 给完整链。
- 结果 meta 行补：分支序号、总耗时、失败原因（失败分支也给页签，内容为错误摘要 + 重跑按钮）。
- 同一分支多次运行只保留最新一份，不累积页签。

#### A5 改动面

| 层 | 改动 |
|----|------|
| 纯函数 | `buildBranches.ts` 增加 `buildRunPlan(steps, edges, selectedIndexes?)`：返回 `{ branches, selectedIndexes, totalStepCount, uniqueStepIds, repeatedStepIds }`，选择索引去重、过滤非法值并按计划顺序排序 |
| 选择 | `PendingRun` 增 `selectedBranchIndexes: number[]`；`runPipeline` 只遍历这些分支；默认全选 |
| 执行 | `executeBranch` 增加 `onStepState(stepId, status)` 回调；`runPipeline` 把每分支状态写入 run session |
| 状态 | `RunSession` 增 `branches: BranchRunState[]`、`unselectedBranchCount: number`；`BranchProgressState` 保留作兼容或退化为派生值 |
| UI | `MainMenu` 增两级选择（新 `BranchPicker.tsx`）；新增 `modules/runs/RunPanel.tsx`、`RunRow.tsx`；`BottomDock` 页签加 `runs`；节点读 `executionStates` |
| i18n | 新增约 28 个键（见 §6.3） |

**收益**：可见、可点、可定位；多分支结果不再混在一起。**不解决**：重复计算、串行、多入边、output 命名。

#### A6 入口：挂进菜单栏的「执行」

可以，且建议这么做。分支选择是「启动一次运行」的一部分，而菜单栏的「执行」已经承担了这个动作；底栏再放一遍，同一件事就会有两个入口。

##### A6.1 行语义

| 标签页状态 | 行点击 | 行尾按钮 | 说明 |
|------------|--------|----------|------|
| 运行中 / 排队 / 待处理 | 切到该标签页 | 取消 / 处理 | 现状不变 |
| 空闲 · 单分支 | 直接运行 | 执行 | 现状不变 |
| 空闲 · 多分支 | 展开分支选择 | 分支 › | 默认全选，确认后开始 |
| 无步骤 | 不动作 | 执行（禁用） | 保持现状 |

- 行尾按钮写的是「接下来会发生什么」，不是固定的「执行」。
- 多分支行的点击也进入选择，不再一键全跑；这正是「让用户确认」的部分。
- 进入选择级前先切到该标签页，背景画布与正在选择的分支一致；关闭菜单不产生 run。
- 单分支 / 单链保持一键运行，零回归。

##### A6.2 菜单面板

- 宽度 240 → 320（固定值，不做宽度动画）；最大高度保持 320。
- 两级：标签页列表 → 分支选择；`‹ 返回` 回上一级，Esc 回上一级、再 Esc 关闭整个菜单。
- 选择级高度：返回行 28 + 全选 24 + 分支行 32/条 + 风险 22 + 底栏 36；分支超过 5 条时只滚动行区，其余固定。
- 风险行只占一行：`输出将被覆盖 3 次`，完整路径放 `title`；只选 1 条时改为中性「写入 1 次」。
- 主按钮：`运行全部 3 条` / `运行所选 2 条` / `选择分支`（禁用）。
- 行悬停时，步数位置换成「只运行」：只以该分支开始，不再二次确认；它不新增一列，320px 仍然放得下。键盘聚焦不显示，避免选中行后常驻。
- 菜单关闭后立即开始；变量补值、跨标签同文件覆盖仍走现有对话框。
- 不用二级 flyout：悬停意图、贴边翻转、嵌套键盘都要另做一套；drill-in 只复用一个面板。

##### A6.3 与底栏的分工

- 菜单 = 选择 + 启动。
- 底栏「运行」= 进度、取消、结果、运行剩余；不再渲染计划页。
- 原型 02 的完整计划页保留为「内容规格」，P0 不挂第二个入口；以后要展开视图，可以从菜单里加「查看详细计划」，而不是同时维护两套选择 UI。

##### A6.4 接缝

| 位置 | 改动 |
|------|------|
| MainMenu props | 增 `branchesByTab`（或 `getTabBranches(tabId)`）与 `onRunTabBranches(tabId, indexes)` |
| 分支摘要 | `{ index, stepNames, stepCount }`；输出冲突由 host 计算 |
| 执行 | `executeForTab(tab, { selectedBranchIndexes })` → `PendingRun.selectedBranchIndexes` |
| 宽度 | `RUN_PANEL_WIDTH` 240 → 320 |
| 状态 | 选择只存在菜单内，关闭即丢弃；不持久化 |

### 方案 B：分段 DAG（Segment DAG）

**一句话**：节点只执行一次；扇出/扇入之间切段；段级并行；中间结果落临时文件。

#### B1 图模型

- 节点 = 步骤，边 = 数据流；入度 0 为源。
- **段（segment）**：从源或扇出点之后开始，穿过连续的单入单出节点，到下一个扇出/扇入点结束。
- 同一段内仍是一条 xan 线性链，一次 `execute_xan_pipeline` 调用。**不按单节点拆进程**：xan 每步一个进程的启动与 IO 开销会把并行收益吃回去。

菱形示例：

```
input → S1: A → ┬→ S2: B → B2 ┬→ S4: D
                └→ S3: C ────┘
```

- 执行顺序：S1 → (S2 ∥ S3) → S4。
- A 只跑一次，D 只跑一次；S2、S3 并行。

#### B2 物化与交接

- 段输出写临时文件，不走 stdout（现行 2MB 截断只适合预览）。
- 目录：`{系统临时目录}/EasyCsv_run_{pid}_{runId}/S{n}.csv`，RAII 清理；失败时保留最近一次供排查（可选）。
- 后端：`execute_xan_pipeline` 增加 `outputFile` 或 `materialize: true`；`pipeline_seq` 已有 `next_temp` 交接机制可复用（`pipeline.rs:1164-1182`）。
- 非 CSV 输入（parquet/duckdb）与相邻 duckdb 段沿用 024 的 `SourceRef` / parquet 交接。

#### B3 调度

- Kahn 拓扑；就绪段进入受限并发（默认 `min(4, 设置里的并发上限)`，与 028 的 tab 级上限分开计数或共享一个池，需拍板）。
- 失败策略沿用 010 的 S5：`continue`（默认，同现状）或 `stop`；失败段的全部下游标 `skipped`。
- 取消：runId 级取消，杀掉所有在跑段并清空就绪队列；已完成的段保留中间文件到本次 run 结束。

#### B4 多入边（必须单独拍板）

三选一：

1. **默认拒绝**：执行前提示「D 有 2 条输入，请用 join/cat 显式合并」。语义最干净，但会让今天能跑的菱形图变成不能跑，回归明显。
2. **按边序拼接**：等价 `cat rows`，保底兼容；节点上标「合并 2 路」，并在日志写清顺序。
3. **`{{input:1}}` / `{{input:2}}` 占位**：join 类命令显式引用前驱段文件。表达力最强，但需要参数表单与变量解析配合。

建议：**B 的第一版只做 2（按边序拼接 + 显式徽标）**，把 3 留给下一稿；1 作为设置项而非默认。

#### B5 输出

- 每个终端段一份结果；output 步骤仍是终端一步。
- 多终端写同一路径时，计划页要求二选一：改路径，或启用占位符 `out-{segment}.csv`（复用 010 S6 的 `{branch}` 思路）。
- 单终端管道行为完全不变。

#### B6 UI

- 画布：同一段的节点之间连线加粗（1.75px），段首节点左上角挂 `S1` 等宽小标；跨段连线中点挂一个文件图标 + `S1.csv`，表示这里有物化。
- 运行面板：一行一段，并行段并排在同一行内（`S2 ∥ S3`），共享一个并行括号。
- 计划摘要：`去重 6 步 · 4 段 · 可并行 2`。
- 节点状态同 A3。

#### B7 改动面与风险

| 项 | 说明 |
|----|------|
| 后端 | `output_file` / materialize 参数、临时目录 RAII、段脚本拼接；duckdb 混合链需单独覆盖 |
| 前端 | 段划分纯函数（含环检测、孤立节点、batch/chart 强制独占段）、调度器、并发池 |
| 特殊节点 | `batch-from/batch-to`、`batch-search`、`chart` 必须各自独占一段，且暂不参与并行 |
| 风险 | 临时文件生命周期、段划分边界、并发下的日志交错、多入边语义回归 |
| 回归红线 | 单链管道（无边或单链）行为与今天逐项一致；旧 `.xanflow` 可执行 |

### 方案 C：管道作业台（Pipeline Jobs）

**一句话**：把「运行」提升为一等对象，一个面板管理所有正在跑 / 排队 / 已完成的管道。

#### C1 作业模型

一条 job = `(tabId, branchIndex)`，字段：名称（`标签页名 › 分支 01`）、状态、开始时间、耗时、输入、输出目标、结果引用、错误。

#### C2 面板

- 位置：底栏「运行」页签的完整形态，或 ViewDock 第五个停靠面板（360px）。
- 分组：运行中 / 排队 / 最近完成（最多 20 条）。
- 行：状态灯、名称、分支链、耗时、输出、操作（取消 / 重跑 / 打开输出 / 只看该 job 的日志）。
- 顶部：`2 运行中 · 1 排队 · 并发上限 4`，可切换上限。

#### C3 与现有层级的关系

现在已有三层：标签页（文档）→ 运行（tab 级 session）→ 分支（路径）。再加 job 会变成第四层，**这是本方案最大的问题**：

- 用户要理解「标签页不是作业，分支才是作业」；
- 执行菜单（MainMenu）已经按标签页列运行，作业台按分支列运行，两处口径不一致；
- 如果 A/B 没做，作业台只是把「分支」换个名字，没有新增能力。

#### C4 建议

不引入 job 概念。把 C 的能力拆进 A/B：

- 跨标签页的「运行中」汇总 → A 的运行面板顶部（已有 `otherRunningCount` 的弱提示，升级为可展开）。
- 单分支重跑 / 只看该分支日志 → A 的行内操作。
- 输出目录 / 结果跳转 → A 的结果页签。

- 不新增全局快捷键（`Alt+R` 已是结果、`Alt+Q` 已是日志）。

## 7. 实施拆分（P0）

1. **纯函数**：`buildRunPlan(steps, edges, selectedIndexes?)` 返回 `{ branches, selectedIndexes, totalStepCount, uniqueStepIds, repeatedStepIds }`；默认全选。配 6 例单测（单链、菱形、混合起点、无边、部分选中、0 条选中）。
2. **菜单第一级**：App 计算 `branchesByTab`（或按需 `getTabBranches`）并传给 `MainMenu`；`RUN_PANEL_WIDTH` 240 → 320；多分支空闲行的行尾按钮改「分支 ›」，行点击进入选择级；单分支保持「执行」。
3. **菜单选择级**：`MainMenu` 增 `pickerTabId` / `selectedIndexes` 状态与 `‹ 返回`；行区滚动、全选、风险行、主按钮按 A6.2；Esc 回第一级。
4. **选择状态**：`executeForTab(tab, { selectedBranchIndexes })`；`PendingRun` 增 `selectedBranchIndexes`；确认后交给调度，菜单关闭。
5. **状态**：`RunSession` 增 `branches: BranchRunState[]`、`unselectedBranchCount`；`runPipeline` 在开始前填充，执行中按回调更新。
6. **执行回调**：`executeSingleBranch` 增 `onStepState`，在 batch / chart / 普通分支三条路径上分别触发。
7. **运行面板**：`RunPanel` + `RunRow`，接 `BottomDock` 的 `runs` 页签；只列选中分支，底部按需渲染「运行剩余」。
8. **节点状态**：`executionStates` 由 App 抬升，`PipelineStepNode` 读取；run 结束后 5 秒清空（与 pill 的 `RUN_PILL_LINGER_MS` 对齐）。
9. **结果页签**：`App.tsx` 的 `dockTabs` 改标签；`ResultMeta` 增分支序号与耗时。
10. **i18n**：中英同步，删掉不再使用的 `results` 计数文案（若保留则兼容）。

每步都能单独合并；第 1、4-6 步无完整 UI 变化，可先落地并补测。

## 8. 验收清单

1. 打开执行菜单：多分支空闲行尾显示「分支 ›」，单分支空闲行显示「执行」，运行中 / 排队行只显示「取消」/「处理」。
2. 点击多分支行或「分支 ›」：菜单进入选择级，默认全选；`‹ 返回` 与 Esc 回第一级，再 Esc 关闭整个菜单。
3. 默认全选：菱形管道显示 2 条分支、输出覆盖 2 次；点主按钮后两条逐条执行。
4. 取消勾选其中一条：已选计数与输出覆盖次数同步变化；主按钮变「运行所选 1 条」；执行后只产生 1 个结果页签。
5. 行尾「只运行」：只执行该分支，其余分支不进入 run，运行面板底部显示「N 条分支未运行 · 运行剩余」。
6. 0 条选中：主按钮禁用并提示「选择要运行的分支」，回车不执行，关闭菜单不产生 run session。
7. 选择级键盘：↑↓ 移动、空格切换、回车运行、Esc 回上一级；进入时焦点在第一行复选框。
8. 点击「运行剩余」：重新打开执行菜单的选择级并预勾选上次未选中的分支，已跑过的分支默认不勾选。
9. 运行面板中每行状态与节点状态一致；当前分支正在跑的节点有左侧竖条，完成后序号填实；未选中分支的节点保持常态。
10. 一条分支失败：该行变红并给出错误摘要；其余选中分支继续；结果页签包含失败分支的错误页，而不是静默消失。
11. 取消整个 run：当前选中分支标「已取消」，剩余选中分支标「已跳过」；按分支取消列为 P1。
12. 单链管道：执行菜单里点行直接运行，不出现选择级，行为与升级前逐项一致（命令、日志、结果、历史、自动存版本）。
13. 结果页签写「分支 01」而非「结果 1」，meta 显示完整链与耗时。
14. 暗色模式下所有状态色取自主题变量，无硬编码色值。
15. 新增文案中英完整；`typecheck` / `eslint` / 全量测试通过。

方案 B 的验收另见 §4 B7 与 010 的 §6；本稿只锁定 A 的验收。

## 9. 开放问题

1. **段级并发与标签页并发是否共享配额**：现在是 `max_concurrent_runs`（默认 4）。段级并行再乘 4 会瞬间拉起 16 个 xan 进程。建议共享一个池，或段级默认 2。
2. **临时文件保留策略**：失败保留、成功删除是最小方案；是否需要「保留最近一次 run」的设置项。
3. **多入边默认行为**：按边序拼接会改变「菱形图今天各跑一次」的结果语义（拼接 vs 二选一），必须在文档与计划页写清。
4. **选择级是否可编辑**：第一版只做勾选；编辑分支 / 改输出路径留给下一稿。
5. **完整计划页是否保留**：P0 只做菜单选择级；原型 02 的 680 宽完整页作为内容规格，不挂第二入口。若以后需要展开视图，从菜单加「查看详细计划」。
6. **菜单里的选择是否覆盖所有空闲标签页**：建议所有多分支空闲行都显示「分支 ›」，`branchesByTab` 的计算成本很低；只做当前标签页可以再省一点。
7. **多分支行点击改为进入选择级**：这是对现有「点行即跑」的行为变更；P0 已采用，单分支保持不变。
8. **按分支取消**：P0 只做整轮取消；要单独停一条，需要给每条分支分配子 runId，或让后端区分「取消当前分支」与「取消整轮」。
9. **超大分支数的上限**：路径枚举在 8 层分叉下会爆炸；选择级要不要在执行前设上限（例如 >32 条分支时要求先简化图）。
10. **选择是否记住**：建议每次默认全选，避免上次漏跑被静默延续；如果用户要求「记住上次选择」，需要额外的持久化与提示。
