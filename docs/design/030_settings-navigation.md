## 0. 结论速览

### 0.1 v2 相对初稿改了什么

初稿只解决「没有目录」。v2 按新需求补两件事,并把它们当**结构**而不是补丁:

| 需求 | v2 的落法 |
|------|-----------|
| **加搜索** | 搜索框在右栏顶部;匹配**标题 + 描述 + `keywords` 别名**;跨分组过滤、保留分组标题、命中子串高亮;侧栏同步降灰 |
| **每个设置一行** | 右栏从「标题 + 描述 + 控件纵向堆叠」改成**三列网格的一行**(标题 / 描述 / 控件);行高 36px,**密度约为现状的 2 倍** |
| 重新设计 | 目录**收敛到分组级**(8 条),条目级查找交给搜索;并把「一项设置」正式定义为「一行」,连带拆掉 AI tab 里那个四按钮的簇(§0.5) |

### 0.2 六个既有问题

| # | 问题 | 证据 |
|---|------|------|
| 1 | 没有目录、分组或页内定位 | `SettingsTabContent.tsx:168-441` 是单列 `space-y-6`;`SettingsDialog.tsx:127-168` 的三段控件只切「大 tab」 |
| 2 | 段落顺序是历史堆积 | 分隔符 / 并发上限 / 主题 / 系统托盘 / 检查更新 / 新手引导同处一列(§1) |
| 3 | 侧向空间浪费,纵向却很长 | 弹窗 `max-w-4xl`(896px),每段只占 `w-1/3`(`:172`)或 `w-[300px]`(`:237`、`:287`) |
| 4 | 无法定位到具体一项 | 帮助中心只能说「设置 → 通用 → 往下滚」,没有锚点可指 |
| 5 | 一处真实归类错误 | `:715-723`「清除执行历史」(`clear_execution_history`)混在 AI tab 的「清除AI学习数据」组里 |
| **6** | **没有搜索** | 想找「托盘」只能靠滚动 + 眼扫;18 项规模下这是主要成本 |

### 0.3 方案一句话

**左栏 = 搜索框(吸顶)+ 分组目录(6 条,当前分组高亮);右栏 = 弱化组名 + 圆角卡片(每卡片一组行,标题 / 描述 / 控件三列)。**
点目录跳到那一组并把焦点移给该组标题;滚动时目录高亮当前分组;**搜索跨分组过滤行,分组标题保留**。

形态对齐 macOS「系统设置」:搜索在侧栏顶部、侧栏是分类、内容区每项设置一行。**目录与搜索分工不同**——
目录回答「我还能去哪」,搜索回答「我要的那一项在哪」;因此目录只到分组级,不再镜像每一个条目(§4.4 有理由)。

### 0.4 两条契约

> **① 行是唯一的一等公民。** 每一项设置 / 动作 = 一行,行 id 稳定,由 `settingsSections.ts` 定义一次;
> 锚点、搜索命中、测试断言全部引用同一个 id。不允许出现「有行没登记」或「登记了没有行」。
>
> **② 分组在侧栏与右栏各出现一次,由同一份数据渲染。** 数量与名称必须一致 ——
> 不允许「目录说 6 组、右栏只有 5 个标题」。两条都由 §7 的契约测试双向比对。

## 2. 问题归因

- **根因不是「设置太多」,而是「没有结构」。** 18 项本身不多,坏在一个都没有分组、没有搜索、
  没有视觉边界(只有 `space-y-6` 的间距),于是只能靠**顺序**承载语义,而顺序又是历史堆积的。
- **「一段设置」占了三行高度。** 现状每个设置是「标题(18px)+ 描述(17px)+ 控件(30px)+ 两处间距」≈ 76px;
  三列成一行后是 36px。**密度翻倍是这次最直接的收益**,目录与搜索都建立在它之上 —— 列表只要还那么长,搜索就只能是补丁。
- **三段控件解决的是「换个话题」,不是「在话题内定位」。** 它天然只能切 3 档;目录 + 搜索才是能随条目数
  线性扩展的形态,而且两者分工不同:目录答「去哪一区」,搜索答「在哪一行」。

## 3. 设计目标与非目标

### 3.1 可验证的目标

1. **按名字找一项 ≤ 3 秒**:`/` 聚焦 → 输入两三个字 → 命中行就在眼前(不再依赖滚动)。
2. **打开弹窗后一屏能看到尽可能多**:行高 36px,1080p 下右栏约显示 18 行里的一半以上,而不是 6~7 段。
3. **滚动位置始终可知**:目录高亮当前分组。
4. **零功能回归**:所有设置的默认值、取值范围、落库时机、文案与 0.7.0 一致(例外只有 §0.5 标注的三处**呈现**变更:归类订正、条件项常显、四按钮拆行)。
5. **无障碍可达**:目录是 `nav` landmark;搜索是 `role="searchbox"` + `aria-label`;当前分组 `aria-current="true"`;
   搜索结果有 `aria-live` 计数播报;命中高亮用 `<mark>`(辅助技术可识别)。

### 3.2 原则(写进代码评审清单)

- **行是唯一的一等公民**(§0.4):id 由分组数据源定义一次,锚点 / 搜索 / 测试共用。
- **搜索是纯函数**:`filterSettings(sections, query) → sections'` 不读 DOM、不读状态,吃数据出数据(§7 直接单测)。
- **不引入第二套状态**:当前分组由滚动位置推导(§4.4),除非用户点了目录(短暂锁定),避免「高亮被上次点击钉住」的错位。
- **危险动作不做整行点击委托**(§4.2):「清除…」类的行只响应按钮本身,避免"点描述就删数据"。

## 4. 方案

### 4.1 整体结构

```
┌─ 设置 ────────────────────────────────────────────────────── ✕ ┐
│ ┌──────────────┬──────────────────────────────────────────────┐ │
│ │ 搜索设置      │  ┌ 搜索框(吸顶)┐                             │ │
│ ├──────────────┤  ├──────────────────────────────────────────┤ │
│ │ 界面          │  │ 系统托盘    关闭窗口最小化到托盘    [✓]    │ │
│ │ 数据与帮助    │  │ 系统通知    执行完成后显示通知      [✓]    │ │
│ │ 窗口行为      │  │ 适配视图    双击画布自动缩放        [✓]    │ │
│ │ 更新          │  │ 更新                                     │ │
│ │ AI            │  │ 检查更新    启动后自动检查新版本    [✓]    │ │
│ │ 插件          │  │ 帮助与数据                                │ │
│ │              │  │ 清除执行历史      删除所有执行历史  [清除]  │ │
│ │              │  │ …(继续滚动)                              │ │
│ │              │  │      [恢复默认]   [保存设置]  ← 浮在底部中间  │ │
│ └──────────────┴──────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

左栏 200px:**搜索框(吸顶)+ 6 条分组**(行高 30px),**没有底部提示行**;**不显示任何计数**(理由见 §4.3 末行)。
右栏:`flex:1`,吸顶搜索框 + 弱化组名 + 圆角卡片(每卡片一组行)。两栏各自滚动。
**底部动作不走底栏**:`恢复默认` / `保存设置` 绝对定位在弹窗**底部中间**(`absolute bottom-3 left-1/2 z-panel`),
**不占一条独立区域**(没有 `border-t`、没有预留高度),列表在它们下面继续滚动。为了让最后一行还能滚出来,
内容区带 `pb-16` 的底部内边距。按钮容器带 `z-panel`(= 10),浮在卡片与行之上(组名已弱化为卡片外小标,见 §11.15),仍低于 `--z-floating: 40` / `--z-modal: 50`。
**`插件` 组自己渲染内容**:它的行是**动态**的(每个目录条目一行,行数随清单变化),所以整组交给 `PluginSection` 而不是走通用行列表;
该组件**只持有一次目录状态**,标题行摘要与下面的行因此不可能对不上。标题行 = `插件` + 摘要(`2/3` · 打开插件目录 · 获取最新版本);
下面依次是:每个插件一行(名称 · 状态 · 项目主页/打开目录/卸载/下载/更新)、一行「下载加速前缀」。原来那块自成一体、与设置页其余部分风格不一致的目录面板已删除 —— `PluginManager` / `PluginRow` 与它们的测试在 §11.12 移除(逻辑仍在 `usePluginCatalog` + `services/plugins`)。

### 4.2 行规范(「每个设置一行」的正式定义)

```css
.settings-row{
  display:grid;
  grid-template-columns:176px minmax(0,1fr) auto;  /* 标题 · 描述 · 控件 */
  align-items:center; gap:16px;
  min-height:36px; padding:0 6px;
  border-bottom:1px solid var(--border-quiet);
}
```

| 列 | 内容 | 规则 |
|----|------|------|
| 1 · 标题 | 设置名(界面原文) | 13px / 500;不换行(过长靠 `title` 提示) |
| 2 · 描述 | 现有 `*Desc` 文案 | 11.5px / `muted-foreground`;**单行** `text-overflow: ellipsis`;窗口变窄时**先截它** |
| 3 · 控件 | 现有控件 | `justify-self:end`;下拉 / 输入 `160px`(API Key `240px`)、三选一 `210px`、开关 16px、按钮自适应;**高度**:输入与下拉默认 `h-8`(32px),但行高只有 36px —— 密集行里一律压到 `h-7`(28px,与数字 / API Key 输入一致),`Select` 已支持 `height` 覆盖(§11.18) |

- **整行可点 = 委托给该行的控件**(开关行点任意处即切换、下拉行点任意处即展开、输入行点任意处即聚焦)。
  与 macOS「系统设置」一致,也是搜索结果里最省事的操作方式。
- **例外:危险行不做整行委托**。`清除执行历史` / `清除对话历史` / `清除反馈记录` / `清除纠正规则` 四行,
  只有按钮本身可点 —— 点描述就删数据是绝不能接受的。
- **例外:`插件` 组的行是运行时生成的**(每个目录条目一行),不来自 `settingsSections`;契约测试只允许这一类额外行(§7 第 3 条)。
- **例外:插件行不做整行点击委托** —— 一行带 2~4 个动作(主页/目录/卸载/下载/更新),没有单一的「激活」语义,委托给下载还会让误点产生几十 MB 流量。
- 行 `id`:`data-settings-row="<id>"`;焦点目标也是这一行(`tabIndex={-1}`),目录跳转后焦点落在这里,
  焦点环用 `focus-visible`,落点在行内第一个可交互元素上(键盘用户 Tab 一次就能操作)。

**为什么不给行加图标**:18 行各配一个图标会把「一眼扫完一列」变成「看图标猜含义」,行高也会被迫加高。
图标一律省掉(分组标题也不加),把可用的高度与注意力全留给「标题 / 描述 / 控件」三列。这是可逆的视觉决定,与功能无关。

### 4.3 搜索规范

**位置:右栏顶部,横跨内容区。** 三个理由:① 搜索过滤的是**列表**,输入框该挨着列表;
② 左栏只有 184px 可用宽,放不下输入框 + 清空按钮;③ 搜索时左栏若整体重排,用户会失去方位感(见下「侧栏同步」)。

| 项 | 规则 |
|----|------|
| 匹配字段 | `title` + `desc` + `keywords`(人工别名表) |
| 分词 | 空格分词,**全部命中**才算匹配(AND);大小写不敏感;中文按**子串**匹配(不做分词) |
| `keywords` 例 | 主题 → `dark / theme / 暗色 / 配色`;系统托盘 → `tray / minimize / 后台`;并发上限 → `concurrency / parallel / 标签页`;分隔符 → `delimiter / sep / tab`;API Key → `token / sk / 密钥 / 凭据` |
| 高亮 | 命中子串包 `<mark>`(底色 `var(--accent-strong)`),标题与描述都高亮 |
| 结果结构 | **保留分组标题,隐藏零命中的分组**;顺序与浏览态一致(不打散、不按相关度重排 —— 设置项不该"跳来跳去") |
| 计数 | **界面上一个计数都不出现** —— 既没有搜索结果数,也没有分组条数(列表本身就是计数)。**清空用输入框内的 ✕ 图标,不用「清除」二字** —— 同一屏已经有 4 个「清除(数据)」按钮,同一个词不能有两种含义。结果的**条数**只走一个 `sr-only` 的 `aria-live="polite"` 播报,供读屏判断「这次搜索剩下几项」,不占任何视觉位置 |
| 侧栏同步 | 不匹配的**分组降为灰色**(不隐藏、不重排,保住方位感);点击灰分组 = **先清空搜索再跳过去** |
| 滚动联动 | **搜索期间关闭**(此时「当前分组」没有意义,继续高亮会误导) |
| 键盘 | 焦点不在任何输入框时按 `/` 聚焦;`Esc` 清空并收起;焦点在搜索框时 `↑`/`↓` 把焦点移到结果行、`Enter` 触发 |
| 空状态 | `没有匹配「<query>」的设置` + 一行建议:`试试「托盘」「暗色」「并发」` |

**为什么不做模糊 / 拼音匹配**:18~20 项规模下,`keywords` 别名表的收益远高于模糊匹配的实现与调参成本;
若将来条目翻倍,再考虑引入(记在 §9 的"暂不做"里,不是永不)。

### 4.4 目录规范

- **搜索框吸顶**,目录在其下滚动(左栏与右栏各自独立滚动)。
- 目录 = **6 条分组**,行高 30px,条目文字右对齐、不带任何数字,容器底部也不放提示行。
- **为什么目录只到分组级,不镜像 18 个条目**:条目级查找已经由搜索承担,再把 18 条塞进 184px 宽的侧栏,
  会有三个代价 —— 行高被压到 18~20px(低于可点尺寸的舒适区)、侧栏在 768px 高的窗口必然滚动、
  以及与右侧列表形成"同一份名单出现两次"的冗余。目录的价值在于**常驻的方位感**,6 条分组足以承担。
- **当前分组高亮**:取「右栏视口顶部之上最近的**分组标题**」为当前分组。基于「元素顶边相对滚动容器顶边」的位置比较(`getBoundingClientRect`,不用 `offsetTop` —— 后者的参照系是 `offsetParent`,在 Radix 的 DOM 里不稳),
  **不用 `IntersectionObserver`**:后者在「分组很短 + 快速滚动」下会在两组之间抖动,
  而 `offsetTop` 比较的语义正是「我现在在哪一组」。用 `requestAnimationFrame` 节流,一个滚动帧只算一次。
- **点击跳转**:平滑滚动到该组标题 → **把焦点移给标题**(`tabIndex={-1}`),因此键盘用户跳过去之后
  Tab 的落点就在这一组的行里,而不是回到页首。
- **点击后的短暂锁定**:平滑滚动期间(约 350ms 或 `scrollend`)暂停高亮更新,
  否则高亮会依次点亮路过的每一组,看起来像"闪一串"。
- **键盘**:焦点在目录内 `↑`/`↓` 移动、`Enter` 跳转、`Home`/`End` 到首尾。目录是 `nav[aria-label="设置目录"]`。

### 4.5 尺寸账

弹窗沿用 `max-w-4xl`(896px)× `h-[72vh]`。**1080p**(72vh ≈ 778px):头部 52 + 底部 56 → 内容区 **670px**。
**768px 高窗口**:内容区 **445px**。

| 区域 | 组成 | 1080p | 768px 窗口 |
|------|------|-------|------------|
| 左栏 | 搜索框 32 + 间距 10 + 6 条分组 × 30 + 内边距 16 | 238 / 670 ✅ | 238 / 445 ✅ 不滚 |
| 右栏 | 吸顶搜索 44 + 8 个分组标题 × 30 + 18 行 × 36 | 902 / 670 → 滚 1.35 屏 | 902 / 445 → 滚 2 屏 |

**对比现状**:现状每个设置 ≈ 76px(标题 + 描述 + 控件三行),18 项 ≈ 1368px + 分组标题 210 = **1578px**;
v2 是 **902px**,**降到 57%**。「滚 2 屏」这件事由搜索兜住 —— 这正是 §2 说的「先有行密度,搜索才有意义」。
也只有在这个行高下,左栏(288px)才能在任何窗口高度下都不滚动。

### 4.6 备选:去掉侧栏(记为开放问题 1)

搜索一旦覆盖「按名字找」,侧栏的价值只剩「我还能去哪」+「当前在哪个分组」。去掉侧栏后右栏从 696px 变成 856px,
每行描述可用宽度从约 380px 增到约 540px —— 这实际上是 VS Code 的形态(搜索在顶 + 分组列表,无侧栏)。
代价:① 丢掉「滚动到哪一组」的常驻指示;② 丢掉「同组内跳转」;③ 与最初「要有目录」的诉求冲突。
**本稿保留侧栏**;切换成本很低(§4.1 的两栏是同一个 flex 容器,去掉左栏即可),原型里留了说明。

### 11.2 与本文档不一致的地方(实施时改了,都有理由)

1. **实际是 8 组,不是 7 组。** 文档 v2 多处写成「7 组 / 7 条」,而树一直是 数据读取 / 并发上限 / 界面 / 窗口行为 / 更新 / 帮助与数据 / AI / 插件 = **8 组**(§0.5 的表格与原型都是 8 条,是正文写错了)。已全文订正。**(并发上限后于 §11.17 并入数据读取,现为 7 组。)**
2. **搜索额外匹配「分组名」,且命中分组名时整组保留**(不只保留命中的行)。理由:插件组没有行(整块面板),否则「插件」「xan」根本搜不到;顺带让「界面」这类分类名也能被搜到。`filterSettings` 与它的测试都覆盖了这条。
3. **滚动联动用 `getBoundingClientRect` 做顶边比较,而不是 `offsetTop`。** `offsetTop` 的参照系是 `offsetParent`,在「Radix Viewport → 内层 wrapper → 内容」这套结构里不稳;换成「元素顶边 − 滚动容器顶边」语义相同,且不依赖定位祖先。容器本身仍通过 `[data-radix-scroll-area-viewport]` 解析(取不到时退回传入的根元素,所以测试里塞一个普通 div 也能跑)。
4. **新增了 7 条描述文案。** 行布局要求「一行一描述」,而 `语言` / `主题` 原本没有描述、四个「清除…」原本共用一条组级描述(`aiClearDataDesc`)、`自定义服务商设置` 本来就没有。于是新增 `settingsLanguageDesc` / `settingsThemeDesc` / `clearExecutionHistoryDesc` / `aiClearConversationsDesc` / `aiClearFeedbackDesc` / `aiClearCorrectionsDesc` / `aiCustomProviderSettingsDesc`。**这是行布局的必要代价,不是顺手改文案** —— §0.5 里「唯一的内容变更只有三处呈现」这句话应读作「三处**结构性**呈现变更,外加行布局必然带来的描述补齐」。
5. **三选一行(语言 / 主题)不做整行点击委托。** 三选一没有单一的「激活」语义,整行点击只能把焦点丢给第一个按钮,反而误导。委托规则的实际范围:开关(委托 = 切换)、下拉与输入(委托 = 聚焦,下拉因此展开)、普通按钮、展开;危险行与三选一不委托。
6. **`/` 与 `Esc` 按 §4.3 落地**:焦点不在任何输入框时 `/` 聚焦搜索;**有查询时第一次 `Esc` 只清空搜索,第二次才关闭弹窗**(搜索框 ✕ 的 `aria-label` 用的也是这条文案)。

### 11.5 修复记录:吸顶分组标题盖住滚动条(2026-10-11,用户报回)

**现象**:滚动时,只要分组标题滑到滚动条所在的高度,滚动条就整段看不见。

**根因**:分组标题是我加的 `sticky top-0` **外加 `z-10`**(当时的想法是「压住滚过去的行」),而标题用 `-mx-4 px-4` 横跨到内容区右边缘 —— 正好是滚动条轨道的位置。Radix 的滚动条是 `position: absolute` 覆盖在内容之上的,`z-index: auto`;`z-10` 的标题因此**画在滚动条之上**,把它盖住了。两个细节让这件事只在「滚动条可见时」暴露:Radix 默认 `type="hover"`,滚动条**只在悬停该面板时才挂载**(不悬停时 DOM 里根本没有滚动条元素 —— 这也是我第一次用静态探针查不到它的原因)。

**修复两处**:
1. `SettingsTabContent.tsx`:去掉分组标题的 `z-10`。`position: sticky` 本身已经让它画在(静态的)行之上;而滚动条是 Viewport **之后**的兄弟节点,同层时后出现的画在上面 —— 去掉 z-index 后滚动条自然回到标题之上。原位留了注释说明为什么**不能**再给它加 z-index。
2. `ScrollArea.tsx`:`ScrollBar` 增加 `z-panel`(= `--z-panel: 10`),让滚动条稳定地待在内容之上。这修的是同一类问题 —— **任何带 z-index 的吸顶头都可能盖住滚动条**,不只设置页这一处;滚动条用 `z-panel` 与面板同层,仍低于 `--z-floating: 40` / `--z-modal: 50` / `--z-toast: 60`,不会盖住浮层。

**验证**(无头 Chromium + stub Tauri,悬停触发滚动条挂载后取层叠栈):

### 11.18 分隔符下拉压到 28px(2026-10-11,用户反馈)
