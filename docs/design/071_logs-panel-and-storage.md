## 1. 现状审计

| 观察 | 影响 |
|---|---|
| 运行日志只存在 `useLogs` 的 `useState`(纯内存),重启全丢 | 排错时不敢关窗口;报错文案无法跨会话反查输入形态 |
| 面板是 600×300 右下角**浮动**窗,与画布/数据预览抢位置 | 与血缘/版本控制等侧栏形态割裂;小窗口下遮挡数据表 |
| 日志是**平铺的时间序列** | 设计 028 并发执行后,多标签页日志交错,分不清哪行属于哪次执行;每行挂标签页徽标是补丁 |
| 级别过滤是 Select、标签页范围是两个文字按钮 | 挤在标题栏;计数藏在下拉里,点空级别像没反应 |
| 无文本搜索 | 「报错文案反查输入形态」(如 header 错 → 分隔符不对)只能靠肉眼滚 |
| 执行历史(SQLite `execution_history.db`,100 条)只有摘要 | 从历史看不到当时的报错全文;两个概念(历史/日志)无关联键 |

## 2. 方案总览

1. **面板形态**: 浮动窗 → **停靠内容区底部的抽屉**(标题栏之下、全内容区宽)。拖上边缘调高、可最大化覆盖画布。默认高 260px,记忆高度。
2. **结构**: 一次执行 = 一个**运行组**。组头 = 状态点 + 标签名 + 开始时间 + 耗时 + 行数 + 级别小计 + 复制全部/重跑;组内行 = 时间 + 级别点 + 消息(hover 复制)。app 级日志(无 tabId)归入可折叠的「应用」组。执行中的组置顶,完成组按开始时间倒序。
3. **过滤/检索**: 级别 Select 改 **chips(带计数)**,与标签页 scope、搜索框为 AND;搜索命中数「命中 n / 总数」,↑/↓ 在命中间跳转,IME 组字不执行;命中词下划线着色。
4. **持久化(存放位置)**: 日志落盘 `<数据目录>/data/logs/easy-csv-YYYY-MM-DD.log`,**按天滚动的 JSONL**;重启回填昨天+今天;保留天数默认 7(0–90,0 = 不落盘),启动时清理超期文件。
5. **出口**: 头部新增「导出日志」(导出当前过滤后的可见行)与「打开日志目录」(复用 `reveal_paths`);Toast(027 §4.3)加「查看日志 / 打开目录」动作。
6. **完成提示文案**(2026-11-22 反馈): 「执行完成」不显示行数,显示**完成时间 + 耗时**(如 `执行完成 14:32:09 · 1.2 s`);日志里的完成行同理(`输出 <bytes>,完成于 HH:mm:ss,耗时 <duration>`),行数/列数只在执行历史摘要里出现。

## 3. 存放位置: 为什么是 JSONL 而不是 SQLite

| 维度 | JSONL 按天滚动(选定) | 塞进 execution_history.db |
|---|---|---|
| 数据性质 | 审计流水: grep、整文件带走 | 结构化记录: 按状态/时间查询、裁剪 100 条 |
| 清理 | 删过期文件,一步到位 | DELETE + VACUUM 才回收 |
| 损坏面 | 单天文件损坏不影响其它天 | 库损坏全丢 |
| 依赖 | 无;写失败可静默降级纯内存 | 与执行历史共用 OnceLock 连接,引入耦合 |

**分工不变**: 执行历史 = 摘要(哪次跑、几行、几字节、快照哈希);日志 = 全文(当时逐条发生了什么)。通过 `runId` 关联但不互写。

## 4. 数据模型

- `LogEntry` 扩展: `runId?: string`(tab 内每次执行生成一个)、落盘用 ISO `ts` 字符串。
- JSONL 一行一条(UTF-8 无 BOM,追加写):

```json
{"ts":"2026-11-22T14:37:13.482+08:00","level":"error","tabId":"t_a3f1","tabName":"库存清洗","runId":"r_9c2e","message":"xan groupby: cannot safely cast Bytes(\"N/A\")"}
```

## 5. 写入与容量纪律

- 前端 `addLog` 同步内存 + 异步 `append_log` invoke 落盘;**落盘失败静默降级**,日志系统永不反打断业务。
- 内存列表上限 500 行(旧的移出内存,文件仍在)。
- 单行上限 8 KB,超出截断加省略标记;单文件超 5 MB 滚动为 `.old`(同日最多一份)。
- 启动时: 回填昨天+今天尾部日志(只读,不可单行删除)→ 清理超保留期文件。

## 6. Rust 新命令(`storage.rs`)

| 命令 | 职责 |
|---|---|
| `append_log(entry: String)` | 追加一行到当天文件;必要时滚动 `.old` |
| `read_recent_logs(days: u32)` | 读近 N 天文件尾部(供回填) |
| `clear_log_files()` | 清空全部日志文件(清空面板时可选联动) |
| `reveal_logs_dir()` | 复用 `reveal_paths` 打开 `data/logs/` |

设置页(040 结构)新增「日志」组: 保留天数 Select(0/7/30/90,默认 7)+ 文件大小展示 +「打开日志目录」。

## 7. 明确不做

| 不做 | 原因 |
|---|---|
| 自动日志上报/遥测 | 本地工具,用户隐私优先 |
| 把全文 stdout 塞进执行历史 | 历史保持摘要;全文已有日志文件承担 |
| 日志面板里内嵌执行历史 | 两个入口各司其职,头部 ◱ 按钮保留跳转 |
| 改画布连线手势 / 给未连线节点加日志提示 | 设计 027 红线 ①② |

## 8. 测试要点(实现阶段展开)

- 运行分组: 并发两 tab 的日志按 `runId` 归组、组内行不再带标签页徽标、「应用」组收纳无 tabId 行。
- 过滤: chips 计数、级别×scope×搜索 AND、IME 组字回车不触发跳转。
- 落盘: `append_log` 失败静默、8 KB 截断、5 MB 滚动 `.old`、保留天数清理(0 = 不写文件)。
- 回填: 重启后「来自磁盘」行只读、日期分隔线、清空按钮的双确认文案。

## 9. 实施记录(2026-11-22)

实现与原型逐条对齐,四处刻意偏差:

| 偏差 | 原因 |
|---|---|
| ~~Frame 04 的完成 Toast 未重新加入~~ → **2026-11-22 已按用户反馈恢复** | 完成反馈 = Toast(成功: `执行完成 {time} · {duration}` + 「查看日志 / 打开目录」两个动作;失败: `执行失败 · {duration}` + 「查看日志」;取消不弹)。Toast 组件扩展支持多动作(`actions[]`);**执行不再自动打开日志抽屉**(原 `setShowLogPanel(true)` 已删),查看日志只能通过 Toast 动作或手动入口 |
| 搜索命中高亮用**主题色**(`text-primary` + `bg-primary/15`) | 2026-11-22 反馈:浏览器默认 `<mark>` 是黄底黑字,不随主题;设置页搜索的 `<mark>` 仍是默认样式,如需统一另行处理 |
| 新增设置「自动弹出日志」(默认关,2026-11-22 反馈) | 设置 → 日志组的开关(`auto_show_log_panel`);开启时恢复执行开始即打开抽屉的旧行为,默认关 = 由完成 Toast 的「查看日志」打开 |
| 保留天数用数字步进器而非 Select | 与「并发上限」共用同一 `number` 控件(settingsSections 的 control 复用),语义等价,0–90 由前端 clamp + 后端 clamp(0..=90)双保险 |
| 清空按钮只清内存 | 磁盘文件由保留天数统一管理;「清空并删文件」的确认文案未做,避免一个按钮两种破坏性 |
| 重跑通过 `runTab(tabId)` | 会切换到该标签页再执行(复用现有执行入口的校验/变量提示/并发排队),与原型「组头重跑」语义一致 |
