工具菜单:正在运行的那个工具

工具菜单里的八件事都是「开一个对话框 → 点开始 → 等」。「工具」菜单本身只是八个入口:点开、关掉,它就退回一张白纸 —— 哪怕后台那次合并还在跑。三个方案,都在菜单里给正在跑的工具留一句话。

本轮只给原型,不动代码。方案 A 直接在条目右端写状态,不新增结构;推荐它。
1

现状:关掉对话框 = 一切归零

八个对话框都是模态的(fixed inset-0 z-50),但它们全都允许在运行中关掉:点背景、点 ×、按 Esc 都直接 onClose。关掉之后后端那条 invoke 还在跑,菜单里却没有任何迹象。

八个入口,零状态。菜单只回答「有哪些工具」,不回答「哪件事正在发生」。

代码里能读到的三个事实:

  • 能关掉,但不会停。合并中「开始」是禁用的,关闭按钮却没有拦 —— 关掉对话框,后端照旧跑完。
  • 成功时没有任何回声。handleMerge 成功只写 localStorage 与本地 state;对话框已关闭时,这次结果要等下次打开「合并工作簿」才看得见。只有失败才弹 toast(if (!isOpen) onShowToast(...))。
  • 用户以为关掉就是取消。于是重复打开同一个工具再点一次开始,两个进程写同一个输出文件。

菜单是最合适的位置:它本来就列着这八件事,而且对话框关掉后它是唯一还能看到工具的地方。

3

状态怎么来、什么时候消失

运行态现在是各对话框自己的 useState,对话框一关就没了 —— 要显示在菜单里,必须抬到 App。一个 toolRuns 表就够:

项取值
状态来源Record<ToolId, { startedAt: number }>,存在 App;八个对话框在开始处 begin(tool)、finally 里 end(tool)(它们已经有 setIsMerging 这类开关,改一行即可)
计时用现有的 RunTimer(工具对话框里本来就在用它),格式沿用它的 0.4 s / 1:04,等宽数字;不上进度百分比 —— 八件事都是一次 invoke,后端没有进度事件
出现条件该工具有进行中的运行。同时跑两个就两行各自带状态,不汇总、不置顶(菜单位置稳定优先)
结束结束时该行状态立刻消失,恢复成普通条目;成功若对话框已关闭,补一条 toast(与失败现有的 onShowToast 对齐)
点运行中的条目重新打开该工具的对话框(上次参数在 localStorage 里),里面「开始」处于禁用态并显示「已有一次运行在进行」;不做「取消」——合并/拆分都没有取消命令,画一个按不动的按钮比不画更糟
不做菜单项不加进度条、不加徽标数字、不做「最近一次运行」——后者是另一个设计(结果面板已经存在,但只在打开对话框时可见)

为什么是 A。菜单的回答对象是「哪件事在发生」,状态就该长在那件事的名字旁边;B 会在一个 226px 宽的菜单里把同一个名字写两遍,C 只有计时没有词。A 的代价最小:一行 32px 内多 70px 文本,七行不动。

落地清单(采纳 A 时):useToolRuns hook + App 里传 begin/end 给八个对话框(各自改两行)+ MainMenu 的 Tools 段按 toolRuns 渲染右端 + 一条「成功后 toast」的补丁 + 两个测试(无运行时不渲染状态、有运行时渲染计时)。
